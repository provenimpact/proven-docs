== Technical Context

Proven Docs is a Node.js ESM CLI tool for converting AsciiDoc documentation to publishable artifacts. The core rendering pipeline (AsciiDoc → HTML → PDF) is implemented and working. The pipeline uses a headless Chromium-based browser for PDF printing, with Mermaid diagram rendering and source code syntax highlighting.

The system uses `playwright-core` (API-only, no browser management) instead of the full `playwright` package. A browser discovery module detects system-installed Chromium-based browsers (Chrome, Edge, Chromium) at runtime, eliminating the need for a ~200 MB browser download on install.

Dependencies: `@asciidoctor/core`, `playwright-core`, `commander`, `mermaid`, `highlight.js`, `chokidar`.

* **Connectivity**: Must work fully offline. No network requests during normal operation.

== Research and Unknowns

All unknowns have been resolved:

* **System browser availability**: `playwright-core` does not manage browsers. The browser discovery module searches well-known installation paths for Chrome, Edge, and Chromium on macOS, Linux, and Windows. The `BROWSER_PATH` environment variable provides an override. This replaces the previous approach of relying on Playwright-managed browser downloads.
* **`page.pdf()` API**: Playwright's `page.pdf()` produces a PDF from the rendered page using Chromium's print-to-PDF engine. It supports `format` (A4, Letter), `printBackground`, `margin`, and other print options. It requires the browser to be launched in headless mode (the default).
* **`@asciidoctor/core` output**: The `convert()` method returns an HTML string (document body). For a complete HTML document with `<html>`, `<head>`, `<body>` tags, set the `standalone` option to `true`. A standalone document is required for proper browser rendering with styles.
* **Mermaid.js browser-side rendering**: The `mermaid` npm package requires a DOM environment. It cannot run in Node.js without a DOM shim. Since we already have headless Chromium, we inject the mermaid library source into the HTML page and let Chromium execute it. The `mermaid.run()` API converts `<pre class="mermaid">` or `<code class="language-mermaid">` elements into inline SVG. The rendering is synchronous from the page perspective — `mermaid.run()` returns a Promise that resolves when all diagrams are rendered.
* **Highlight.js browser-side execution**: highlight.js auto-detects and highlights `<pre><code class="language-xxx">` blocks. Asciidoctor emits `<pre><code>` with language classes. Injecting highlight.js core + `hljs.highlightAll()` into the page highlights all code blocks before PDF printing.
* **Mermaid dependency licensing**: The `mermaid` package and all transitive dependencies use permissive licenses (MIT, ISC, Apache-2.0, BSD). Verified via `license-checker`.
* **Highlight.js licensing**: BSD-3-Clause. Permissive. Satisfies licensing constraint.

== System Design

The feature is a multi-stage pipeline with a CLI entry point. The core pipeline (AsciiDoc → HTML → PDF) is extended with two enrichment stages that operate on the HTML before PDF printing.

=== CLI Entry Point (`src/cli.js`)

Responsibility: Parse command-line arguments, orchestrate the render-then-print pipeline, handle top-level errors, and set exit codes.

Uses Commander.js to define:

* Command: `render <input>` — the primary subcommand
* Positional argument: `<input>` — path to .adoc file (required)
* Option: `-o, --output <path>` — override output file path
* Automatic `--help` generation from Commander

The `render` command handler:

1. Validates the input file exists and is readable
2. Calls the renderer to produce HTML
3. Calls the printer to produce PDF
4. Reports success or failure
5. Exits with appropriate code

=== HTML Enricher (`src/enrich.js`)

Responsibility: Transform Mermaid code blocks and apply server-side syntax highlighting. Exports the mermaid library path for the printer to load via `addScriptTag`.

Exports:

* `enrichHtml(html: string): string` — transforms mermaid blocks into `<pre class="mermaid">`, applies server-side highlight.js, injects highlight.js CSS theme.
* `mermaidJsPath: string` — absolute path to `mermaid.min.js` for the printer to load in the browser.

Implementation:

1. At module load time, read the highlight.js CSS theme (`github.css`) from `node_modules/highlight.js/styles/` and resolve the path to `mermaid.min.js`.
2. **Syntax highlighting (server-side)**: Import `highlight.js` as an npm module. For each `<code data-lang="xxx">` block (non-mermaid), call `hljs.highlight(code, { language })` in Node.js. Replace the raw code with pre-highlighted HTML containing hljs span classes. Inject the `github.css` theme into `<head>`.  Unrecognised languages are left as plain text (highlight.js returns the input unchanged).
3. **Mermaid block transformation**: Transform Asciidoctor's `<pre class="highlight"><code data-lang="mermaid">` elements into `<pre class="mermaid">` elements. The actual mermaid.js rendering happens in `print.js` via `page.addScriptTag` + `page.evaluate` (see below).
4. **Execution order**: Syntax highlighting runs first (server-side), then mermaid block transformation.

NOTE: The original design specified browser-side injection of both mermaid.js and highlight.js. During implementation, we discovered that (a) inline injection of the 2.8MB mermaid.min.js fails in Chromium due to octal escape sequences in strict mode contexts, and (b) highlight.js works natively in Node.js, making server-side highlighting simpler and more reliable. Mermaid rendering was moved to `print.js` using `page.addScriptTag({ path })` which avoids the inline injection issue.

=== AsciiDoc Renderer (`src/render.js`)

Responsibility: Convert AsciiDoc source text to a complete HTML document with correct include resolution.

Exports a single function:

* `renderToHtml(source: string, baseDir?: string): string` — takes raw AsciiDoc text and an optional base directory for include resolution, returns a standalone HTML document string.

Implementation:

1. Import `Asciidoctor` from `@asciidoctor/core`
2. Create a processor instance
3. Build options object: `{ standalone: true, safe: 'safe' }`. When `baseDir` is provided, add `base_dir: baseDir` to the options.
4. Call `processor.convert(source, options)`
5. Return the HTML string

The `standalone: true` option produces a full HTML document (`<html>`, `<head>`, `<body>`) with the default Asciidoctor stylesheet embedded. The `safe: 'safe'` mode restricts file access to `base_dir` and its subdirectories, which is appropriate for a rendering pipeline. The `base_dir` option tells Asciidoctor where to resolve `include::` directives from — when omitted, Asciidoctor defaults to the process working directory, which produces incorrect results when the CLI is invoked from a directory different from the document's directory.

==== Include Resolution Strategy

Every command that processes an AsciiDoc file (render, validate, info) must:

1. Resolve the input file path to an absolute path
2. Derive the base directory from the input file: `path.dirname(absoluteInputPath)`
3. Pass the base directory to the Asciidoctor call (`base_dir` option for `convert()` / `load()`)

This ensures `include::` directives always resolve relative to the document's own directory, regardless of where the CLI is invoked from. Callers that do not use Asciidoctor through `renderToHtml()` (e.g., `validate` and `info` commands which call `asciidoctor.load()` directly) must pass `base_dir` in their own options object.

=== Browser Discovery (`src/browser.js`)

Responsibility: Detect a Chromium-based browser installed on the host system and return its executable path for use by the PDF Printer.

Exports a single function:

* `discoverBrowser(): string` — returns the absolute path to a Chromium-based browser executable. Throws an error if no browser is found.

Implementation:

1. **Environment variable override**: If `BROWSER_PATH` is set, verify the path exists and is executable, then return it. If the path does not exist, throw an error naming the invalid path.
2. **Platform detection**: Use `process.platform` to determine the host OS (`darwin`, `linux`, `win32`).
3. **Well-known path search**: For each platform, check a list of well-known browser installation paths in preference order:

**macOS (`darwin`):**

1. Google Chrome: `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`
2. Microsoft Edge: `/Applications/Microsoft Edge.app/Contents/MacOS/Microsoft Edge`
3. Chromium: `/Applications/Chromium.app/Contents/MacOS/Chromium`

**Linux (`linux`):**

1. Google Chrome: `google-chrome-stable`, `google-chrome` (via PATH lookup)
2. Microsoft Edge: `microsoft-edge-stable`, `microsoft-edge` (via PATH lookup)
3. Chromium: `chromium-browser`, `chromium` (via PATH lookup)

**Windows (`win32`):**

1. Google Chrome: `%PROGRAMFILES%\Google\Chrome\Application\chrome.exe`, `%PROGRAMFILES(X86)%\Google\Chrome\Application\chrome.exe`, `%LOCALAPPDATA%\Google\Chrome\Application\chrome.exe`
2. Microsoft Edge: `%PROGRAMFILES(X86)%\Microsoft\Edge\Application\msedge.exe`, `%PROGRAMFILES%\Microsoft\Edge\Application\msedge.exe`
3. Chromium: `%PROGRAMFILES%\Chromium\Application\chrome.exe`, `%LOCALAPPDATA%\Chromium\Application\chrome.exe`

4. **First match wins**: Return the first browser executable found. The preference order (Chrome > Edge > Chromium) reflects installation prevalence.
5. **Playwright cache fallback**: If no system browser is found, check for a Playwright-cached browser via `chromium.executablePath()` from `playwright-core`. This handles development environments where `npx playwright install` was previously run but no system browser is installed at standard paths. If the cached path exists, return it.
6. **No browser found**: Throw an error with a message listing the supported browsers and the `BROWSER_PATH` environment variable:
+
....
Error: No supported browser found.

proven-docs requires a Chromium-based browser (Google Chrome, Microsoft Edge, or Chromium).

Install one of these browsers, or set the BROWSER_PATH environment variable
to the path of a Chromium-based browser executable.
....

For Linux PATH lookups, use a synchronous check (e.g., `which` or `execFileSync`) to resolve the binary path. For macOS and Windows, use `fs.existsSync()` on the well-known paths.

=== PDF Printer (`src/print.js`)

Responsibility: Take an enriched HTML string, render it in a headless Chromium browser, execute Mermaid rendering if needed, capture console warnings, and print to PDF.

Exports a single function:

* `printToPdf(html: string, outputPath: string): Promise<void>` — launches a headless browser, loads the HTML, renders Mermaid diagrams, prints to PDF, writes the file, and closes the browser.

Implementation:

1. Import `chromium` from `playwright-core`, `mermaidJsPath` from `enrich.js`, and `discoverBrowser` from `browser.js`
2. Detect if the HTML contains `class="mermaid"` blocks
3. Discover browser executable: `const executablePath = discoverBrowser()`
4. Launch a headless browser: `chromium.launch({ executablePath })`
4. Create a new page: `browser.newPage()`
5. Register a `console` event listener on the page to capture `console.warn()` messages from Mermaid error handling. Forward these to `process.stderr`.
6. Set the page content: `page.setContent(html, { waitUntil: 'load' })` — syntax highlighting is already applied server-side by the enricher, so it appears immediately.
7. **If Mermaid blocks exist**: Load mermaid.js via `page.addScriptTag({ path: mermaidJsPath })` — this loads the library from disk into the browser without inline injection issues. Then call `page.evaluate()` to run `mermaid.initialize()` and render each `<pre class="mermaid">` block individually via `mermaid.render()`. Each block is wrapped in a try/catch: successful blocks get their SVG; failed blocks get a styled error indication and emit `console.warn()`.
8. Print to PDF: `page.pdf({ path: outputPath, format: 'A4', printBackground: true })`
9. Close the browser: `browser.close()`
10. Ensure browser cleanup happens even on error (try/finally)

The `printBackground: true` option is important for AsciiDoc documents that use background colors in admonition blocks, code blocks, table headers, and syntax-highlighted code.

=== Error Handling Strategy

Errors are caught at the CLI level and reported to stderr:

[cols="1,2,2", options="header"]
|===
| Error Type | Detection | User Message

| Input file not found
| `fs.access()` before reading
| `Error: File not found: <path>`

| Input file not readable
| `fs.access(R_OK)` failure
| `Error: Cannot read file: <path>`

| AsciiDoc rendering error
| Asciidoctor logs errors via its logger API
| `Error: AsciiDoc rendering failed: <details>`

| No supported browser found
| `discoverBrowser()` throws when no browser is detected
| `Error: No supported browser found.` (with instructions listing supported browsers and BROWSER_PATH)

| Invalid BROWSER_PATH
| `discoverBrowser()` throws when the specified path does not exist
| `Error: Browser not found at path specified by BROWSER_PATH: <path>`

| Browser launch failure
| Playwright throws on `chromium.launch({ executablePath })`
| `Error: Failed to launch browser: <details>`

| PDF write failure
| File system error during write
| `Error: Failed to write PDF: <path>: <details>`
|===

All error paths exit with code 1. Success exits with code 0.

=== Output Path Resolution

Default behavior: replace the input file's `.adoc` extension with `.pdf`.

* `docs/report.adoc` → `docs/report.pdf`
* `/abs/path/spec.adoc` → `/abs/path/spec.pdf`

When `--output` is specified, use the provided path directly. If the output path is a directory, write `<basename>.pdf` into that directory.

== Story Resolution

=== US-001: Convert AsciiDoc File to PDF

Components:: CLI Entry Point, AsciiDoc Renderer, PDF Printer
Criteria::
* When the user runs the render command with a path to an .adoc file, the system shall produce a PDF file in the same directory as the input file → CLI resolves output path from input path, Renderer produces HTML, Printer writes PDF (PDF-001)
* The system shall render the AsciiDoc source to HTML using asciidoctor.js → AsciiDoc Renderer uses `@asciidoctor/core` `convert()` with `standalone: true` (PDF-002)
* The system shall open the rendered HTML in a headless Chromium-based browser and print it to PDF → PDF Printer uses `playwright-core` `chromium.launch({ executablePath })` + `page.pdf()`, where `executablePath` comes from Browser Discovery (PDF-003)
* The system shall save the PDF with the same base name as the input file but with a .pdf extension → Output Path Resolution logic replaces `.adoc` with `.pdf` (PDF-004)
* The system shall complete the conversion without requiring a network connection → Covered by project Connectivity constraint. Browser discovery is a local file-system check; no network calls in the pipeline.

=== US-002: Predictable Output Location

Components:: CLI Entry Point (output path resolution)
Criteria::
* The system shall write the output PDF to the same directory as the input .adoc file → Default output path resolution: replace `.adoc` with `.pdf` in the same directory (PDF-004)
* When the user specifies an output path, the system shall write the PDF to that path instead → `--output` option parsed by Commander, passed to Printer (PDF-005)

=== US-003: Conversion Error Reporting

Components:: CLI Entry Point (error handling)
Criteria::
* If the specified input file does not exist → `fs.access()` check before reading, error message includes file path (PDF-006)
* If the specified input file is not readable → `fs.access(R_OK)` check, error message printed (PDF-007)
* If the AsciiDoc rendering produces errors → Asciidoctor logger captures errors, reported to user (PDF-008)
* If the headless browser fails to launch → Playwright error caught, diagnostic message printed (PDF-009)

=== US-004: CLI Integration

Components:: CLI Entry Point, Executable Entry Point
Criteria::
* The system shall provide a CLI command that accepts an input file path as an argument → Commander `render <input>` command definition (PDF-010)
* When the user runs the command with --help → Commander auto-generates help from command definition (PDF-011)
* The system shall exit with code 0 on successful conversion → CLI handler calls `process.exit(0)` on success path (PDF-012)
* The system shall exit with a non-zero exit code on failure → CLI error handler calls `process.exit(1)` on all error paths (PDF-013)

=== US-005: Mermaid Diagram Rendering

Components:: HTML Enricher, PDF Printer
Criteria::
* When the input AsciiDoc contains a Mermaid source block, the system shall render the Mermaid syntax as a visual diagram → Enricher transforms `[source,mermaid]` blocks into `<pre class="mermaid">` elements, injects mermaid.js; Chromium executes `mermaid.run()` to produce inline SVG (PDF-014)
* The system shall support flowchart, sequence, class, state, C4Context, C4Container, and C4Component diagram types → Mermaid.js natively supports all listed types; no filtering needed (PDF-015)
* The rendered diagrams shall be legible at the PDF page scale → Mermaid's default theme and SVG output scale with the page; `mermaid.initialize()` uses default width which fits A4 (PDF-016)
* The system shall render Mermaid diagrams without requiring a network connection → Mermaid.js source is bundled inline in the HTML; no external requests. Covered by project Connectivity constraint.
* If a Mermaid block contains invalid syntax → Mermaid error handler replaces the block with a styled error message and emits `console.warn()`, which print.js captures and forwards to stderr (PDF-017)
* When an AsciiDoc file contains multiple Mermaid blocks → `mermaid.run()` processes all `<pre class="mermaid">` elements independently; each becomes its own SVG (PDF-018)

=== US-006: Source Code Syntax Highlighting

Components:: HTML Enricher, PDF Printer
Criteria::
* When the input AsciiDoc contains a source code block with a language attribute → Enricher injects highlight.js core and CSS theme; Chromium executes `hljs.highlightAll()` which highlights all `<pre><code class="language-xxx">` blocks (PDF-019)
* The system shall support syntax highlighting for JavaScript, TypeScript, Python, Java, Ruby, Go, Rust, HTML, CSS, JSON, YAML, and shell scripts → highlight.js supports 190+ languages including all listed ones. Common languages are bundled in the core (PDF-020)
* The highlighted code shall use a colour scheme legible when printed on paper → The `github` highlight.js theme uses a light background with sufficient contrast for both screen and print (PDF-021)
* The system shall apply syntax highlighting without requiring a network connection → highlight.js source and theme CSS are bundled inline in the HTML. Covered by project Connectivity constraint.
* When a source code block specifies an unrecognised language → highlight.js silently skips unknown languages, leaving the code as plain monospaced text (PDF-022)

=== US-007: Include Directive Resolution

Components:: CLI Entry Point (`src/commands/render.js`, `src/commands/validate.js`, `src/commands/info.js`), AsciiDoc Renderer (`src/render.js`)
Criteria::
* When the input AsciiDoc contains an `include::` directive with a relative path, the system shall resolve that path relative to the directory containing the input file → Each command derives `baseDir` from `path.dirname(inputPath)` and passes it to the Asciidoctor call as `base_dir` (PDF-023)
* When the user runs the render command from a different directory → `src/commands/render.js` passes `path.dirname(inputPath)` to `renderToHtml(source, baseDir)`, which sets `base_dir` in the Asciidoctor options (PDF-024)
* When the user runs the validate command from a different directory → `src/commands/validate.js` passes `base_dir: path.dirname(filePath)` to `asciidoctor.load()` (PDF-025)
* When the user runs the info command from a different directory → `src/commands/info.js` passes `base_dir: path.dirname(filePath)` to `asciidoctor.load()` (PDF-026)
* If an included file does not exist at the resolved path → Asciidoctor reports the missing include via its logger; validate reports it as an error, render produces a warning in stderr (PDF-027)

=== US-008: System Browser Detection

Components:: Browser Discovery (`src/browser.js`), PDF Printer (`src/print.js`)
Criteria::
* The system shall detect and use an existing Chromium-based browser (Google Chrome, Microsoft Edge, or Chromium) installed on the host system → `discoverBrowser()` searches well-known installation paths per platform and returns the first match (PDF-028)
* When multiple supported browsers are installed, the system shall select one using a consistent preference order → Search order is Chrome > Edge > Chromium; first found wins (PDF-029)
* When the user sets the BROWSER_PATH environment variable, the system shall use that browser instead of auto-detecting → `discoverBrowser()` checks `process.env.BROWSER_PATH` first, before platform search (PDF-030)
* If no supported browser is found and BROWSER_PATH is not set, then the system shall exit with a non-zero exit code and print an error message listing the supported browsers and how to set BROWSER_PATH → `discoverBrowser()` throws with a descriptive message; CLI catches and exits with code 1 (PDF-031)
* The system shall detect browsers on macOS, Linux, and Windows without requiring additional configuration → Platform-specific path lists for `darwin`, `linux`, and `win32` are built into `src/browser.js` (PDF-032)
* The system shall not require a Playwright-managed browser download for normal operation → `playwright-core` replaces `playwright`; no postinstall browser download (PDF-033)
