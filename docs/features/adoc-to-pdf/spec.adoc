= Specification: AsciiDoc to PDF
:version: 1.2.0
:source-stories-version: 1.2.0
:last-updated: 2026-03-07
:feature: adoc-to-pdf
:prefix: PDF
:toc:

== PDF-001
When the user runs the render command with a path to an .adoc file, the system shall produce a PDF file in the same directory as the input file.

Type:: Event-driven
Source:: US-001: Criterion 1
Verification:: Run the render command with a valid .adoc file. Confirm that a PDF file appears in the same directory as the input file.

== PDF-002
The system shall render AsciiDoc content to HTML before converting it to PDF.

Type:: Ubiquitous
Source:: US-001: Criterion 2
Verification:: Provide an .adoc file containing AsciiDoc formatting (headings, lists, bold text). Run the render command. Open the resulting PDF and confirm that all AsciiDoc formatting is faithfully represented.

== PDF-003
The system shall produce the PDF by printing the rendered HTML in a headless browser.

Type:: Ubiquitous
Source:: US-001: Criterion 3
Verification:: Run the render command on a valid .adoc file. Confirm that a PDF file is produced. Confirm that the PDF content matches the rendered HTML (layout, fonts, styles are consistent with browser rendering).

== PDF-004
The system shall name the output PDF with the same base name as the input file, using a .pdf extension.

Type:: Ubiquitous
Source:: US-001: Criterion 4, US-002: Criterion 1
Verification:: Run the render command on a file named `report.adoc`. Confirm the output is named `report.pdf` in the same directory. Repeat with files named `my-spec.adoc`, `README.adoc`, and confirm naming follows the same pattern.

== PDF-005
When the user specifies an output path, the system shall write the PDF to that path instead of the default location.

Type:: Event-driven
Source:: US-002: Criterion 2
Verification:: Run the render command with an .adoc file and an explicit output path argument. Confirm the PDF is written to the specified path, not the default location.

== PDF-006
If the specified input file does not exist, then the system shall exit with a non-zero exit code and print an error message that identifies the missing file by name.

Type:: Unwanted behavior
Source:: US-003: Criterion 1
Verification:: Run the render command with a path to a file that does not exist. Confirm the process exits with a non-zero code and the error message includes the file path.

== PDF-007
If the specified input file is not readable, then the system shall exit with a non-zero exit code and print an error message.

Type:: Unwanted behavior
Source:: US-003: Criterion 2
Verification:: Run the render command with a path to a file that exists but has no read permissions. Confirm the process exits with a non-zero code and an error message is printed.

== PDF-008
If the AsciiDoc rendering produces errors, then the system shall report the rendering errors to the user.

Type:: Unwanted behavior
Source:: US-003: Criterion 3
Verification:: Run the render command with an .adoc file containing malformed content. Confirm that rendering errors are reported to the user via standard error output.

== PDF-009
If the headless browser fails to launch, then the system shall exit with a non-zero exit code and print a diagnostic message.

Type:: Unwanted behavior
Source:: US-003: Criterion 4
Verification:: Run the render command in an environment where the browser binary is unavailable. Confirm the process exits with a non-zero code and a diagnostic message is printed indicating the browser launch failure.

== PDF-010
The system shall provide a CLI command that accepts an input file path as a positional argument.

Type:: Ubiquitous
Source:: US-004: Criterion 1
Verification:: Run the CLI with a file path as a positional argument. Confirm the system accepts it and attempts conversion.

== PDF-011
When the user runs the command with --help, the system shall display usage information describing available arguments and options.

Type:: Event-driven
Source:: US-004: Criterion 2
Verification:: Run the command with --help. Confirm that usage information is printed, including the input file argument and any options.

== PDF-012
When conversion completes successfully, the system shall exit with code 0.

Type:: Event-driven
Source:: US-004: Criterion 3
Verification:: Run the render command with a valid .adoc file. Confirm the process exit code is 0.

== PDF-013
When conversion fails, the system shall exit with a non-zero exit code.

Type:: Event-driven
Source:: US-004: Criterion 4, US-003: Criterion 1, US-003: Criterion 2, US-003: Criterion 4
Verification:: Run the render command with an invalid input (missing file, unreadable file, broken browser). Confirm the process exit code is non-zero in each case.

NOTE: Offline operation is enforced by the project-wide Connectivity constraint ("The tool must work fully offline. No network requests are required during normal operation.") and is not duplicated here.

== PDF-014
When the input AsciiDoc contains a Mermaid source block, the system shall render the Mermaid syntax as a visual diagram in the PDF output.

Type:: Event-driven
Source:: US-005: Criterion 1
Verification:: Create an .adoc file containing a `[source,mermaid]` block with a valid flowchart definition. Run the render command. Open the resulting PDF and confirm that the Mermaid block is rendered as a visual diagram, not raw text.

== PDF-015
The system shall support rendering the following Mermaid diagram types: flowchart, sequence, class, state, C4Context, C4Container, and C4Component.

Type:: Ubiquitous
Source:: US-005: Criterion 2
Verification:: Create an .adoc file containing one Mermaid block for each supported diagram type. Run the render command. Open the resulting PDF and confirm that each diagram type renders as a recognisable visual diagram.

== PDF-016
The system shall render Mermaid diagrams at a size that is legible at the PDF page scale without manual zooming.

Type:: Ubiquitous
Source:: US-005: Criterion 3
Verification:: Create an .adoc file containing a Mermaid flowchart with at least 8 nodes. Run the render command. Open the PDF at 100% zoom and confirm that all labels and connections are readable.

== PDF-017
If a Mermaid block contains invalid syntax, then the system shall include an error indication in the PDF output at the location of the diagram and print a warning to stderr.

Type:: Unwanted behavior
Source:: US-005: Criterion 5
Verification:: Create an .adoc file containing a Mermaid block with deliberately invalid syntax. Run the render command. Confirm that the PDF contains an error indication where the diagram would appear and that stderr includes a warning message referencing the invalid block.

== PDF-018
When an AsciiDoc file contains multiple Mermaid blocks, the system shall render each block as a separate diagram.

Type:: Event-driven
Source:: US-005: Criterion 6
Verification:: Create an .adoc file containing three distinct Mermaid blocks (e.g., a flowchart, a sequence diagram, and a state diagram). Run the render command. Open the PDF and confirm that all three diagrams are rendered independently in their respective positions.

== PDF-019
When the input AsciiDoc contains a source code block with a language attribute, the system shall apply syntax highlighting to the code in the PDF output.

Type:: Event-driven
Source:: US-006: Criterion 1
Verification:: Create an .adoc file containing a `[source,javascript]` block with a function definition. Run the render command. Open the PDF and confirm that keywords, strings, and comments are rendered in distinct colors.

== PDF-020
The system shall support syntax highlighting for at minimum the following languages: JavaScript, TypeScript, Python, Java, Ruby, Go, Rust, HTML, CSS, JSON, YAML, and shell scripts.

Type:: Ubiquitous
Source:: US-006: Criterion 2
Verification:: Create an .adoc file containing one source block for each listed language with representative code. Run the render command. Open the PDF and confirm that each block has syntax-specific color highlighting.

== PDF-021
The system shall apply a syntax highlighting color scheme that remains legible when the PDF is printed on paper.

Type:: Ubiquitous
Source:: US-006: Criterion 3
Verification:: Run the render command on a file with syntax-highlighted code blocks. Print the PDF on a black-and-white printer. Confirm that highlighted elements remain distinguishable from each other and from the background.

== PDF-022
If a source code block specifies a language that the system does not recognise, then the system shall render the code block as plain monospaced text without highlighting.

Type:: Unwanted behavior
Source:: US-006: Criterion 5
Verification:: Create an .adoc file containing a `[source,nonexistent_lang]` block. Run the render command. Confirm that the code is displayed as plain monospaced text in the PDF without errors and without highlighting.

== PDF-023
When the input AsciiDoc contains an `include::` directive with a relative path, the system shall resolve that path relative to the directory containing the input file.

Type:: Event-driven
Source:: US-007: Criterion 1
Verification:: Create a directory structure with `parent/main.adoc` containing `include::sub/chapter.adoc[]` and `parent/sub/chapter.adoc` existing. Run the render command from a directory other than `parent/`. Confirm the include resolves correctly and the included content appears in the output.

== PDF-024
When the user invokes the render command from a working directory different from the input file's directory, the system shall resolve include directives relative to the input file's directory, not the working directory.

Type:: Event-driven
Source:: US-007: Criterion 2
Verification:: Place `index.adoc` (with an include directive) and its included file in `project/docs/`. Run `proven-docs render project/docs/index.adoc` from the project root. Confirm the PDF is produced with the included content present.

== PDF-025
When the user invokes the validate command from a working directory different from the input file's directory, the system shall resolve include directives relative to the input file's directory.

Type:: Event-driven
Source:: US-007: Criterion 3
Verification:: Place an .adoc file with an include directive and its included file in a subdirectory. Run `proven-docs validate <subdirectory>/file.adoc` from the parent directory. Confirm no false errors are reported for the include.

== PDF-026
When the user invokes the info command from a working directory different from the input file's directory, the system shall resolve include directives relative to the input file's directory.

Type:: Event-driven
Source:: US-007: Criterion 4
Verification:: Place an .adoc file with an include directive and its included file in a subdirectory. Run `proven-docs info <subdirectory>/file.adoc` from the parent directory. Confirm document metadata is extracted without include-related errors.

== PDF-027
If an included file does not exist at the resolved path, then the system shall report an error identifying the missing file.

Type:: Unwanted behavior
Source:: US-007: Criterion 5
Verification:: Create an .adoc file with an `include::` directive pointing to a non-existent file. Run the render command. Confirm that an error or warning is reported that identifies the missing file path.
