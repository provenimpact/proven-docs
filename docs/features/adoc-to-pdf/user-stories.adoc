= User Stories: AsciiDoc to PDF
:version: 1.2.0
:last-updated: 2026-03-07
:feature: adoc-to-pdf
:toc:

== US-001: Convert AsciiDoc File to PDF
As a documentation author,
I want to convert an AsciiDoc file to a PDF,
so that I can produce a print-ready document for distribution.

Acceptance Criteria:

* [ ] When the user runs the render command with a path to an .adoc file, the system shall produce a PDF file in the same directory as the input file.
* [ ] The system shall render the AsciiDoc source to HTML using asciidoctor.js.
* [ ] The system shall open the rendered HTML in a headless Chromium browser and print it to PDF.
* [ ] The system shall save the PDF with the same base name as the input file but with a .pdf extension (e.g., report.adoc produces report.pdf).
* [ ] The system shall complete the conversion without requiring a network connection.

== US-002: Predictable Output Location
As a documentation author,
I want the PDF output to appear alongside my source file by default,
so that I can find it without guessing where it went.

Acceptance Criteria:

* [ ] The system shall write the output PDF to the same directory as the input .adoc file.
* [ ] When the user specifies an output path, the system shall write the PDF to that path instead.

== US-003: Conversion Error Reporting
As a documentation author,
I want clear error messages when conversion fails,
so that I can diagnose and fix problems quickly.

Acceptance Criteria:

* [ ] If the specified input file does not exist, then the system shall exit with a non-zero exit code and print an error message identifying the missing file.
* [ ] If the specified input file is not readable, then the system shall exit with a non-zero exit code and print an error message.
* [ ] If the AsciiDoc rendering produces errors, then the system shall report the rendering errors to the user.
* [ ] If the headless browser fails to launch, then the system shall exit with a non-zero exit code and print a diagnostic message.

== US-004: CLI Integration
As a documentation author,
I want to invoke the conversion from the command line,
so that I can integrate it into scripts and CI pipelines.

Acceptance Criteria:

* [ ] The system shall provide a CLI command that accepts an input file path as an argument.
* [ ] When the user runs the command with --help, the system shall display usage information.
* [ ] The system shall exit with code 0 on successful conversion.
* [ ] The system shall exit with a non-zero exit code on failure.

== US-005: Mermaid Diagram Rendering
As a documentation author,
I want Mermaid diagram blocks in my AsciiDoc files to render as visual diagrams in the PDF,
so that I can include architecture diagrams, flowcharts, and sequence diagrams without external tooling.

Acceptance Criteria:

* [ ] When the input AsciiDoc contains a Mermaid source block (e.g., `[source,mermaid]`), the system shall render the Mermaid syntax as a visual diagram in the PDF output.
* [ ] The system shall support the Mermaid diagram types: flowchart, sequence, class, state, C4Context, C4Container, and C4Component.
* [ ] The rendered diagrams shall be legible at the PDF page scale without manual zooming.
* [ ] The system shall render Mermaid diagrams without requiring a network connection.
* [ ] If a Mermaid block contains invalid syntax, then the system shall include an error indication in the PDF output and print a warning to stderr.
* [ ] When an AsciiDoc file contains multiple Mermaid blocks, the system shall render each one independently.

== US-006: Source Code Syntax Highlighting
As a documentation author,
I want source code blocks in my AsciiDoc files to render with syntax highlighting in the PDF,
so that code examples are readable and visually distinguishable from prose.

Acceptance Criteria:

* [ ] When the input AsciiDoc contains a source code block with a language attribute (e.g., `[source,javascript]`), the system shall apply syntax highlighting to the code in the PDF output.
* [ ] The system shall support syntax highlighting for commonly used languages including JavaScript, TypeScript, Python, Java, Ruby, Go, Rust, HTML, CSS, JSON, YAML, and shell scripts.
* [ ] The highlighted code shall use a color scheme that is legible when printed on paper.
* [ ] The system shall apply syntax highlighting without requiring a network connection.
* [ ] When a source code block specifies an unrecognized language, the system shall render the code block without highlighting rather than failing.

== US-007: Include Directive Resolution
As a documentation author,
I want AsciiDoc include directives in my documents to resolve relative to the document's own directory,
so that I can run the tool from any working directory and my multi-file documents render correctly.

Acceptance Criteria:

* [ ] When the input AsciiDoc contains an `include::` directive with a relative path, the system shall resolve that path relative to the directory containing the input file, not the current working directory.
* [ ] When the user runs the render command from a directory different from the input file's directory, the system shall still resolve includes correctly.
* [ ] When the user runs the validate command from a directory different from the input file's directory, the system shall still resolve includes correctly.
* [ ] When the user runs the info command from a directory different from the input file's directory, the system shall still resolve includes correctly.
* [ ] If an included file does not exist at the resolved path, then the system shall report an error identifying the missing file.
